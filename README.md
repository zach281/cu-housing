# Campus Nest

A housing marketplace for CU Boulder students: apartments, rooms, subleases, lease takeovers, and roommates.
"Campus Nest" is a working name, set in `src/lib/site.ts`.

**Stack:** Next.js 16 (App Router, Cache Components) · TypeScript · Tailwind CSS 4 · Supabase (Postgres, Auth, Storage) · Vercel

## Setup

1. **Create a Supabase project** at supabase.com (free tier is fine).

2. **Install and configure**
   ```bash
   npm install
   cp .env.example .env.local
   ```
   Fill in `.env.local` from Supabase → Project Settings → API: the project URL and the **publishable** key.
   Never put the secret / service-role key in this app.

3. **Apply the database schema**
   ```bash
   npx supabase login
   npx supabase link --project-ref <your-project-ref>
   npx supabase db push
   ```
   No terminal? Paste each file in `supabase/migrations/` into the Supabase SQL Editor and run them **in
   filename order**. Every file is safe to run once; later files assume the earlier ones have run.

4. **Configure Auth in the Supabase dashboard** (the CLI config only applies to local dev):
   - Authentication → Sign In / Providers → Email: turn on **Confirm email**.
   - Authentication → URL Configuration: Site URL `http://localhost:3000`; add redirect URL `http://localhost:3000/**`
     (and your Vercel URL later).
   - **Email templates are optional.** The app works with Supabase's default templates. The custom ones in
     `supabase/templates/` let people confirm on a different device than they signed up on; Supabase only
     lets you edit templates once custom SMTP is set up (below).
   - Authentication → Policies (password): minimum 8 characters, letters and digits.
   - **Custom SMTP is required before launch.** Without it, Supabase only emails members of your Supabase
     organization (anyone else gets "Email address not authorized"), sends a few emails per hour, and locks the
     templates. Add a sender such as Resend or Postmark under Authentication → Emails → SMTP Settings. This needs
     a domain you own. Until then, invite any address you want to test with to your Supabase organization.

5. **Run it**
   ```bash
   npm run dev
   ```

### Sample listings

- **Local development:** `supabase/seed.sql` holds 24 fictional Boulder listings and 5 demo owners
  (password `demo-password-1`). `supabase db reset` and `e2e/up.sh` load it automatically.
- **Live site (optional):** to see Browse populated before real listings exist, run
  `supabase/demo/add-demo-listings.sql` in the Supabase SQL Editor. Titles start with "[Demo]", the demo
  accounts can't sign in, and there are no photos. Remove them with `supabase/demo/remove-demo-listings.sql`.
- Both are generated by `python3 scripts/seed/generate.py`; edit that file, not the SQL.

### Make yourself an admin
Roles can't be changed from the app. In the Supabase SQL editor:
```sql
update public.profiles set role = 'admin'
where id = (select id from auth.users where email = 'you@example.com');
```

### Regenerate database types after schema changes
```bash
npx supabase gen types typescript --linked > src/lib/supabase/database.types.ts
```

## Testing

```bash
npm run check      # typecheck + lint + unit tests
npm run build      # production build (needs the env vars set)
TEST_DATABASE_URL=postgres://postgres@localhost:5432/postgres npm run test:db
```

### End-to-end tests (real browser, local Supabase-like stack)

```bash
cd e2e && npm install && cd ..
bash e2e/up.sh                 # Postgres + Supabase Auth + PostgREST + storage emulation + the app on :3100
cd e2e && npm test             # Playwright tests in e2e/tests
```

`e2e/up.sh` downloads the official Supabase Auth and PostgREST binaries, runs every migration, and starts
the app against them, so sign-up emails, Row Level Security and storage permissions behave as in production.
Linux only; it needs a disposable local Postgres (it creates one under `/var/tmp/pgtest` if missing).

`test:db` applies every migration to a throwaway database on any Postgres 15+ server, then runs
`supabase/tests/rls.test.sql`: about 100 assertions covering what each role can and can't read or write.
It drops and recreates a database named `cu_housing_test`. Never point it at production.

## How it's built

```
src/
  proxy.ts                 Refreshes the Supabase session; early redirect for protected routes
  app/
    page.tsx               Landing page
    (auth)/                Sign up, sign in, forgot password + their server actions
    auth/confirm/          Handles links from auth emails
    auth/signout/          POST-only sign out
    account/               Profile, verification status, password change
  lib/
    auth.ts                getCurrentUser / requireUser (server-only data access layer)
    supabase/              Browser, server and proxy clients; generated types
    validation/            Zod schemas shared by forms and server actions
    site.ts                Brand name and campus constants
    listings/              Listing constants, data access, address lookup, photo helpers
    validation/listing.ts  Rules for every listing field (shared by forms and server actions)
  app/listings/new/        Step 1 of a new listing
  app/dashboard/listings/  My listings, the step-by-step editor, and listing server actions
supabase/
  migrations/              Schema, RLS policies, storage buckets
  templates/               Auth email templates
  tests/                   RLS test suite + Postgres stubs for running it without Supabase
```

### Security model
- Every table has Row Level Security. The app uses only the publishable key, so the database enforces who can
  see and change what, regardless of the UI.
- Users can edit only their name, bio and photo. Role, verification and suspension are changed by database
  triggers or admins.
- **CU verification** is automatic: confirming an `@colorado.edu` email sets it, and changing to a non-CU email
  removes it. **Provider verification** is a manual admin step. Badges describe what was checked; they never
  claim a listing is safe.
- Analytics events are written only through `track_event()`, which stamps the caller's identity.
- Listings: at most 15 photos each and 10 new listings per user per day (admins exempt), enforced in the
  database. Photos are resized in the browser before upload, which also strips GPS data from phone photos.
- Signed-out visitors never receive a listing's street address or exact coordinates (column privileges in
  migration 6). They see the neighborhood, distance from campus, and a map pin snapped to a ~250 m grid.
- Addresses are looked up with the free U.S. Census geocoder (no account); posters can drag the map pin.
  Map tiles come from OpenStreetMap.
- No payments are processed.
